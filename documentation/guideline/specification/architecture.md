# Aposma Architecture

## 1. Architectural idea

Aposma is a **grounded code-intelligence pipeline**. Its defining architectural decision is the separation between:

1. **program facts**, discovered deterministically; and
2. **natural-language interpretation**, generated by the SLM.

This separation reduces hallucination risk and makes the system easier to test.

## 2. Data flow

```text
Source repository
      |
      v
Clang/LLVM frontend
      |
      v
AST / analysis events
      |
      v
Raw findings
      |
      v
Evidence normalization
      |
      +----> persistence
      |
      v
Finding ranking
      |
      v
Context selection
      |
      v
Local SLM
      |
      v
Structured review / documentation
```

## 3. Deterministic layer

The deterministic layer exists to answer questions such as:

- What symbol is this?
- Where is it declared?
- What source location is associated with it?
- What AST relationship exists?
- What known analysis rule was triggered?

When a fact can be answered by the compiler/toolchain, that route should be preferred over asking the SLM.

## 4. Evidence layer

The evidence layer is the contract between analysis and reasoning.

An evidence record should be:

- explicit
- serializable
- source-located when possible
- stable enough to test
- minimal enough to fit useful model context

Conceptually:

```text
Finding
  ├── identity
  ├── severity
  ├── category
  ├── source location
  ├── evidence references
  ├── structural context
  └── optional source excerpt
```

## 5. Ranking layer

Not every finding deserves equal attention.

The ranking layer may consider:

- severity
- confidence
- scope of impact
- source location quality
- evidence completeness
- whether the issue appears new in a diff

Ranking must be deterministic and inspectable.

## 6. Model layer

The model layer receives a constrained context rather than an unrestricted repository dump.

A model request should conceptually contain:

```text
SYSTEM INSTRUCTIONS
       +
ANALYZER EVIDENCE
       +
RELEVANT SOURCE CONTEXT
       +
OUTPUT SCHEMA
```

The model should be explicitly instructed:

- not to invent source locations
- not to claim facts absent from evidence
- to acknowledge uncertainty
- to separate observed facts from suggestions
- to produce machine-parseable output where possible

## 7. Persistence

Persistence exists for history, reproducibility, and comparison.

A useful analysis record includes:

```text
analysis_id
repository
commit or revision
timestamp
analyzer configuration
finding count
model configuration
result metadata
```

The persistence layer should not be required for one-off deterministic analysis.

## 8. Git integration

Git should provide context rather than become the source of program semantics.

Potential uses:

- changed-file detection
- changed-line detection
- commit association
- historical comparison
- regression-oriented review

## 9. GitHub integration

The intended integration boundary is a GitHub App / webhook workflow.

Conceptually:

```text
GitHub event
    |
    v
Aposma service
    |
    v
Checkout revision
    |
    v
Analyze
    |
    v
Build evidence
    |
    v
Generate review
    |
    v
GitHub Check Run
```

GitHub integration should remain separable from the core analysis engine.

## 10. Failure model

### Analyzer unavailable

Return a clear infrastructure error. Do not silently fall back to model-only claims about code structure.

### Model unavailable

Return deterministic findings and indicate that AI explanations were unavailable.

### Malformed model output

Reject or repair only when safe and deterministic. Preserve raw output for debugging where appropriate.

### Partial analysis

Mark incomplete analyses explicitly. Never present partial information as a complete repository assessment.

## 11. Extensibility

The following should be replaceable independently:

- analyzer rules
- evidence schema versions
- ranking policy
- model backend
- persistence backend
- report renderer
- GitHub adapter

This allows Aposma to evolve without coupling all components together.
